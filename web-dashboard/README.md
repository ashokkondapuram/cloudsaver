# CloudSaver web dashboard

Next.js 16 App Router, React 19, TypeScript and Tailwind CSS 4 frontend. The inventory uses TanStack Table for filtering/sorting and TanStack Virtual for row rendering at 10,000+ rows. The local `components/ui/button.tsx` is an owned shadcn-style primitive; there is no external design-service dependency.

Product baseline: see the [root README](../README.md) (currently `main` @ `39def45`). Resource lists call `GET /api/v1/scans/{scan_id}/resources` with default **`cost_scope=billable`** so free topology rows (NIC, NSG, and similar) stay out of the primary cost workspace unless they have findings or billing evidence. Pass `cost_scope=all` to include every merged inventory row.

## Run locally

Use Node.js **24.22.1 or newer** (`nvm use` from the repository root). Start the API gateway first using the main project README. Then:

```bash
cd web-dashboard
npm ci
API_GATEWAY_URL=http://127.0.0.1:8000 npm run dev
```

Open `http://127.0.0.1:3000`. Enter the workspace access key generated during backend setup. It is retained in React memory only; reloading the page clears it. Use localhost for development and HTTPS for any hosted environment.

The browser calls same-origin `/api/v1/*` endpoints. A narrowly scoped Next route handler forwards these calls to the operator-configured `API_GATEWAY_URL`. The API key is forwarded in the Authorization header, not a URL. The gateway URL is a server-side runtime setting and is not baked into frontend JS.

## Production build

```bash
npm run typecheck
npm run build
API_GATEWAY_URL=http://127.0.0.1:8000 npm start
```

The supplied Dockerfile builds with Node.js 22 and starts the standalone server as the `node` user on port 3000. Set `API_GATEWAY_URL=http://api-gateway:8000` in the container runtime, as the root compose file does. The Docker build excludes host dependencies, build output and environment files.

## Supported workflow

- Connect with a pre-provisioned workspace access key.
- Run read-only Azure/AWS/GCP/Kubernetes scans for explicitly provisioned sources.
- View saved scan history and select a prior scan.
- Search, filter by rule/severity, sort columns and inspect resource evidence in the **Resources** workspace and nine-tab resource drawer (Overview, Findings, Evidence, Costs, Observability, AI, Decision, History, Code).
- Export the selected complete scan as JSON or CSV. CSV neutralizes spreadsheet formula prefixes.
- For supported live disk/IP findings, download a remediation review script generated by the API. Downloading does not execute it. Historical synthetic snapshots cannot produce exports.

Live dollar values are shown as “Not estimated” until the backend has supported billing estimates. No synthetic spend trends or savings claims are shown. There is no Gemini integration in this application.

## Current boundaries

The engineering MVP uses manually provisioned workspace keys rather than a browser Entra OAuth/SSO flow. The web app displays billing/operations and durable delivery history. Operators configure schedules and tenant targets; admins can inspect dead letters and explicitly replay notifications with duplicate-risk acknowledgment. Interactive multi-cloud scans remain synchronous. See the root roadmap for production release work. Visual QA in a real browser and external Azure credentials are required before any production launch.

## Browser acceptance checks

With the built dashboard running, install a Playwright Chromium browser with `npx playwright install chromium` (or select an existing binary with `CLOUDSAVER_BROWSER_EXECUTABLE`) and run `npm run test:e2e`. `CLOUDSAVER_DASHBOARD_URL` selects the test dashboard URL. For the enterprise control-plane, FinOps ladder, governance, and related UI regressions only, run `npm run test:enterprise-ui` (Playwright `enterprise-ui` project). See `e2e/ENTERPRISE_UI.md` for the maintained spec list, governance/workloads deep-link conventions, and cross-view refresh behavior. The full dashboard suite runs both Playwright projects via `npm run test:e2e`. The suite intercepts API calls with test-only fixtures; it verifies admin replay acknowledgment, Viewer restrictions, escaped audit text and mobile layout without sending alerts or scanning clouds. Backend RLS, roles and delivery recovery are tested separately against disposable PostgreSQL/Redis by the root verification runner.
