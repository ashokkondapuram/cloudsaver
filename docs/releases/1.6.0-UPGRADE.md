## Upgrade

1. Back up core/identity databases and recoverable keys/peppers using the approved recovery procedure. Validate restoration in isolation. Never delete customer volumes or regenerate identity peppers to recover a migration.
2. Use one matching source artifact/image set. Stage a supported upgrade from `0021_billing_jobs` to the Alembic head **`0022_financial_outcomes`**. Identity's independent graph is unchanged at **`i0013_multicloud_analysis_catalog`**.
3. In the development Compose environment, run from the CloudSaver folder:

   ```sh
   docker compose --env-file .env up --build migrate
   docker compose --env-file .env up -d --build
   docker compose --env-file .env logs --no-color --tail=100 migrate scanner-service api-gateway
   ```

   Existing `.env`, tenant history, keys, CLI cache and named volumes remain. Windows PowerShell can use `--env-file .\.env` with the same commands. Python installation is not required on the Windows host for these Docker commands. The migration bootstrap safeguards and platform identity password recovery from 1.5.1 remain in force.
4. Check dependency-aware `/readyz` and a signed-in tenant journey through the customer dashboard. Open **Savings & investigations**. Viewer must see the finance boundary; finance/admin can read; human gates must reject workspace keys. Validate both the API gateway and actual dashboard proxy.
5. Empty `CLOUDSAVER_EVIDENCE_SOURCES=[]` is safe: cases and investigations work, but financial outcomes stay unknown without signed evidence. Configure reviewed collector grants and the core-only `CLOUDSAVER_EVIDENCE_KEY_OUTCOMES` secret only after finance/security approves the evidence integration. Restart scanner-service to apply a changed environment. These are not portal/client credentials.
6. Smoke-test import/correction/deduplication, ownership history, a complete signed savings case, independent finance review and negative outcomes with authorized staging evidence. Existing automatic readers still report unverified coverage. Enabling a reader does not make its data resource-attributed or invoice-reconciled.

The migration adds new financial/ownership tables and expands the existing savings-case state check without rewriting legacy history. New case payload schema is 2; old cases stay retained and read-only in this workflow. Downgrade can remove the new empty schema, but refuses once any new ownership/financial/investigation audit history or schema-2 case exists. A refused downgrade rolls back transactionally and preserves forced RLS. Recovery with customer history requires a reviewed data-preserving plan; do not bypass the guard or delete records to make rollback pass.

## Verification and artifact inventory

`scripts/release_manifest.py` derives migration heads from both Alembic graphs and hashes the exact tracked release bytes (excluding only its own manifest). After staging source changes, regenerate with `python scripts/release_manifest.py`; verify with `python scripts/release_manifest.py --check`. Git identifies the full tree. The manifest is not an image signature or production attestation.

CI retains core, platform, worker, portal, dashboard, real-stack, security and release-inventory gates. The aggregate 85% critical Python coverage threshold now includes `outcome_evidence`, `outcome_store`, `outcome_api` and `outcome_anomalies` alongside the six inherited critical modules. Regression scenarios cover synthetic signed evidence, financial revisions/negative demand normalization, health/coverage gaps, source revocation, exact ledger matching, cross-tenant RLS, append-only privileges, concurrent reconciliation, ownership history, anomaly correction/deduplication, proxy route contracts, human approval boundaries and accessible browser journeys. Tests use synthetic data and do not certify provider invoices, production IAM or the HA/recovery architecture.

Repository administrators must still enforce required checks/human review through branch protection or rulesets. This release preserves those external launch gates.
