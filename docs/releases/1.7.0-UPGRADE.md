## Upgrade and deployment

1. Back up the core and independent identity databases and recoverable keys/peppers under the approved recovery policy. Include audit anchors in restoration planning. Never delete customer volumes or rotate identity peppers to repair an upgrade.
2. Use one matching artifact/image set. This branch's core Alembic head is **`0026_control_plane`**, after `0025_observability_connectors` and `0024_cloud_commitments`. Identity's independent graph remains **`i0013_multicloud_analysis_catalog`**. The new control-plane tables have forced RLS and a populated-history downgrade guard. They are domain/storage foundations, not a newly enabled execution API. Preserve existing records and use the feature acceptance matrix before promoting the branch.
3. For local development Compose:

   ```sh
   docker compose --env-file .env up --build migrate
   docker compose --env-file .env up -d --build
   docker compose --env-file .env logs --no-color --tail=100 migrate scanner-service governance-monitor
   ```

   Windows PowerShell can use `--env-file .\.env` with the same commands. These Docker commands do not require Python on the Windows host. Preserve existing `.env`, customer data, database volumes and developer CLI cache. Existing role-bootstrap and identity password-recovery safeguards remain in force.
4. The new `governance-monitor` is a local database worker, not an agent executor. Ensure it is supervised in the chosen production platform and can reach the core database. It requires the configured governance verifier secrets as described below. Keep dependency-aware serving readiness, infrastructure monitoring and trusted-proxy/TLS controls from the hardening runbook.
5. Empty `CLOUDSAVER_GOVERNANCE_SOURCES=[]` keeps signed ingestion disabled. Cases and assessments can be reviewed, but implementation, compensation and independent verification cannot be invented. Configure approved sources and the secret `CLOUDSAVER_GOVERNANCE_KEY_PRIMARY` in **core and dedicated governance-monitor only**. Custom key references need explicit mappings in both. Neither browser nor execution agent should receive these keys.
6. Sign in with the configured verified human identity. A human TenantAdmin delegates governance responsibilities; a ComplianceReviewer reviews the policy and owner before a SecurityAnalyst evaluates the new dedicated Azure storage flag. A shared workspace key is not a human approval credential. Review the inherited Entra policy and full-scope pilot restriction before enabling this journey.
7. Run a fresh owned Azure inventory scan. Existing snapshots that lack `allow_blob_public_access` remain unknown. Validate the complete staged treatment with actual authorized provider event and application-access attestations; a mock receipt is not customer acceptance.

The upgrade does not add an infrastructure write permission, merge a GitOps request, execute a plan or call a model. Optional work links retain their existing independent approval/permit boundaries. Existing financial outcomes and production authentication controls remain intact.

## Rollback and history

The runtime role has forced tenant RLS and only reviewed mutable columns for finding/risk/exception state. Control revisions, delegations, assessments, evidence, action bindings and event history are append-only. A downgrade can remove an **empty** new schema, but refuses once governance records or monitor history exist. A refused downgrade rolls back without leaving FORCE RLS disabled. Customer-history recovery requires a reviewed data-preserving procedure; do not remove records to bypass the guard.

The dedicated worker records a heartbeat even without findings. Stopping it does not delete that audit/operational history or make a destructive downgrade safe. Restoring data and verifier secrets needs a coordinated review of in-flight approvals, exceptions, reattestations, provider outcomes and externally retained audit anchors.
